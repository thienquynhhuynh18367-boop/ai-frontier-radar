# GitHub Search 数据质量审查（2026-10-14）

## 已发布批次与可复核事实

2026-10-12（Asia/Shanghai）正式批次的 `receivedCount=356`、`acceptedCount=36`、`itemCount=36`。356 是八组 Search 查询返回的候选数，36 是经过仓库字段校验、公开/非归档/非 Fork 与 `windowStart <= pushed_at < windowEnd` 精确 UTC 过滤、再按仓库数字 ID 合并后的唯一仓库数。中间 320 个候选不能直接解释为“320 个无关仓库”：当时没有保存逐查询拒绝原因，且同一仓库可能在多个查询中出现。

已保存 RawItem 的搜索命中证据中，`enterprise-ai=33`、`large-language-model=3`；其他六个查询没有入选条目。这是**发现查询**分布，不等于 Classification（规则分类）分布。最终分类的 `enterprise-ai=33`、`agent=25`、`rag=11`、`mcp=6`；同一仓库可命中多个主题。前四项合计不能用作去重后的总数。

## 受控复核与 Root Cause Analysis（根因分析）

新增 `npm run radar:diagnose -- --date 2026-10-12`，沿用原 Query、50 条第一页、9 秒请求间隔与精确过滤，但**只输出安全的逐页数量，不写入 Raw、历史或 latest**。诊断不记录 URL、响应正文、Token 或仓库信息。该次受控请求因网络错误仅有两组拿到有效页：

| Query | API 候选 | 无效字段 | 窗口前 | 窗口后 | 精确窗口内 | 状态 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| `agent` | 50 | 0 | 0 | 50 | 0 | 第 1 页成功 |
| `mcp` | 50 | 0 | 0 | 50 | 0 | 第 1 页成功 |
| 其余六组 | 未取得有效页 | 未知 | 未知 | 未知 | 未知 | 网络错误，不能下结论 |

该上海自然日的实际 UTC 窗口为 `2026-10-11T16:00:00.000Z` 至 `2026-10-12T16:00:00.000Z`，结束点不包含。GitHub Search 的 `pushed:2026-10-11..2026-10-12` 以日期缩小范围，仍可返回 UTC 10 月 12 日 16:00 后的仓库；因此本地毫秒级过滤不可移除。受控结果说明：`sort=updated` 的第一页与宽于业务窗口的日期 Query 组合，至少在 `agent`、`mcp` 两组造成第一页全落在窗口后。每组只取一页，因此有效窗口内的潜在后续结果没有被看到。当前证据不足以证明其他六组的确切淘汰原因，也不能证明改用另一排序或分页能稳定改善覆盖。

本次保留原采样配置和精确过滤，不为了提高条目数放宽公开性、Fork、归档或时间标准，也不补造不存在的主题。后续可在额度允许的情况下，用单组 Query 对比严格 UTC 时间限定、分段日期或额外一页的命中质量；先验证 GitHub Search 对时间限定的实际语义与限流成本，再决定是否改策略。

## 发布门槛

现有 50% 骤降规则会在上次 36 条、本次少于 18 条时拒绝更新 latest。由于当前每组只取一页、样本较小且主题覆盖偏斜，合法的日间变化也可能触发该规则。现阶段保留它作为防止异常空批次覆盖上一份有效数据的保守保护；积累更多真实业务日后应结合逐查询诊断与来源覆盖，重新校准门槛。`empty`、`partial`、`failed`、`schema_failed` 和 `anomaly` 不会被写成新成功批次。
