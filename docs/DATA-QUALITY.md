该上海自然日的实际 UTC 窗口为 `2026-10-11T16:00:00.000Z` 至 `2026-10-12T16:00:00.000Z`，结束点不包含。GitHub Search 的 `pushed:2026-10-11..2026-10-12` 以日期缩小范围，仍可返回 UTC 10 月 12 日 16:00 后的仓库；因此本地毫秒级过滤不可移除。受控结果说明：`sort=updated` 的第一页与宽于业务窗口的日期 Query 组合，至少在 `agent`、`mcp` 两组造成第一页全落在窗口后。每组只取一页，因此有效窗口内的潜在后续结果没有被看到。当前证据不足以证明其他六组的确切淘汰原因，也不能证明改用另一排序或分页能稳定改善覆盖。

本次保留原采样配置和精确过滤，不为了提高条目数放宽公开性、Fork、归档或时间标准，也不补造不存在的主题。后续可在额度允许的情况下，用单组 Query 对比严格 UTC 时间限定、分段日期或额外一页的命中质量；先验证 GitHub Search 对时间限定的实际语义与限流成本，再决定是否改策略。

## 发布门槛

现有 50% 骤降规则会在上次 36 条、本次少于 18 条时拒绝更新 latest。由于当前每组只取一页、样本较小且主题覆盖偏斜，合法的日间变化也可能触发该规则。现阶段保留它作为防止异常空批次覆盖上一份有效数据的保守保护；积累更多真实业务日后应结合逐查询诊断与来源覆盖，重新校准门槛。`empty`、`partial`、`failed`、`schema_failed` 和 `anomaly` 不会被写成新成功批次。

## 第三阶段受控对照与改进（2026-10-15）

用相同的 2026-10-12 上海自然日窗口（UTC `2026-10-11T16:00:00Z` 至 `2026-10-12T16:00:00Z`），在匿名 Search API 上低频比较。下表是每个请求返回的前 50 个候选，经本地半开窗口过滤后的数量；没有保存完整响应。单组第一页为 1 次请求，第二页或分段各再消耗 1 次；匿名 Search 有独立限流，不能无限增加页数。

| Query / 方案 | 请求数 | 候选 | 精确窗口内 | 窗口前 | 窗口后 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `agent` 日期限定 + updated 第 1 页 | 1 | 50 | 0 | 0 | 50 |
| `agent` 日期限定 + updated 第 2 页 | 额外 1 | 50 | 0 | 0 | 50 |
| `agent` 日期限定 + best match 第 1 页 | 1 | 50 | 20 | 12 | 18 |

| `agent` 分段：10 月 11 日日期限定 | 1 | 50 | 46 | — | — |
| `agent` 分段：10 月 12 日日期限定 | 额外 1 | 50 | 0 | — | — |

分段方案第一段能找到窗口前八小时中的有效数据，但第二段的第一页仍被窗口后数据挤占；要覆盖整日还需更多分页。**采用 UTC 时间戳限定并保留原 `sort=updated`、一页 50 条及本地精确过滤**，每组仍只消耗 1 次请求。GitHub Search 对时间戳限定并未实现毫秒级半开语义：实测仍有 6–7 条窗口后结果，所以 Collector 的 `[windowStart, windowEnd)` 判断不可删除。`agent` 与 `mcp` 是受控样本，不据此宣称 GitHub 搜索全量覆盖。

2026-10-14 上海业务日的一次正式配置运行：GitHub 八组共收到 361 个候选，通过精确过滤并按仓库 ID 合并后接受 280 个。修复 HN URL query 安全边界后，按相同固定窗口再次真实运行，GitHub 仍收到 361 个候选但接受 275 个。Search 实时索引会变化；固定 `asOf` 只保证**固定 Raw 输入可重算**，不能保证两次联网响应字节相同。最终发布的 Raw 快照和逐查询统计可复核。`queryStats.accepted` 是该 Query 的过滤通过数，多个 Query 命中同一仓库时，各组之和可能大于来源去重后的 `acceptedCount`。多来源 Pipeline 的异常保护按来源执行，GitHub 某轮显著少于其上次有效量时只沿用其旧条目并标为 `anomaly`，不把坏采样当作全站行业下降。当前仍只有两个真实业务日且中间缺日，任何 7/30/90 天增长率均显示历史不足。

## 第四阶段历史批次时间标注

2026-10-14 批次的 `asOf=2026-10-15T00:00:00.000Z` 在当时实际采集执行时仍属未来。其 Raw、历史条目、评分和来源健康时间不能被当作精确的真实采集时刻；本次保留全部数据，不倒填一个猜测的时间，不删除已提交历史。该日 `data/2026-10-14/items.json` 与当前发布 latest 增加可选 `qualityFlags=["as_of_was_future_at_collection"]`，网站横幅展示警示；旧 Schema Version 仍可读。后续合法的新批次不会继承此标记。作为趋势输入时，这个业务日的观测数量仍是实际返回的候选样本，但任何以该日 `asOf`、`firstSeenAt` 或评分时效为依据的历史结论都需谨慎；连续 14/60/180 天证据条件仍必须满足。

## 第四阶段首次云端运行的计数契约修复

首次 Daily Radar 云端运行中，arXiv 和 OpenAI 相比上次有效批次出现超过 50% 的条目骤降，按既定规则隔离其当轮有效新条目并沿用旧来源条目；GitHub Search、HN、Anthropic 及招聘来源取得新数据。此前发布契约仍把隔离条目计入 `acceptedCount`，却未计入送往去重的 `normalizedCount`，因此整批被误判为 `schema_failed`，旧 latest 按保护规则未覆盖。修复后 v2 快照单独记录 `excludedCount`，保留 `rejectedCount` 的格式拒绝语义，并在 Schema 中核对三者关系。异常来源继续标为 `anomaly`，沿用条目保留旧 `collectedAt`；不得将部分成功说成六源全部刷新。
